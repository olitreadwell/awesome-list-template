# Automation inventory

Every automation worth having in an awesome list repo, with what it catches,
what it costs, and where it runs. `SPEC.md` decides which of these the template
ships; this file is the full menu it chooses from.

No row depends on GitHub Actions. The contract is `ci/check.sh` plus the scripts
in `jobs/`. Anything the maintainer has, a laptop with `launchd`, a VPS with
`systemd` or `cron`, or any CI provider, runs the same code. The GitHub Actions
adapter exists in `ci/adapters/` and is not installed by default.

The engine is Python 3.12 to 3.14 (`uv`, `ruff`, `mypy --strict`, `pytest`).
Node is installed only as tooling for `awesome-lint`, Prettier, and Pagefind.
The site is opt-in: rows marked **opt-in**, plus everything in A3 except the
exports, only run when `site.enabled = true` in `awesome.toml`.

Where it runs:

- **hook**: local git hook, before the commit or push leaves the machine.
- **job**: a script in `jobs/`, run on a schedule by `launchd`, `systemd`, or
  `cron`, and runnable by hand at any time.
- **cli**: a command a human runs.
- **platform**: a GitHub platform feature that is not Actions, such as issue
  forms, deploy-from-branch Pages, or Dependabot.
- **adapter**: optional, only if the maintainer adds a CI provider.

Verdict keys: **ship** (default on), **opt-in** (shipped, off until enabled in
`awesome.toml`), **document** (written up in `docs/`, not wired), **skip**
(with reason).

## Excluded, with reasons

- GitHub Actions as the pipeline. It is a fine runner, but it is not the only
  one, and the template should not stop working when a repo moves, when a
  workflow is disabled, or when an org blocks Actions. `ci/check.sh` plus
  `jobs/` keeps every check runnable on a laptop. The Actions adapter ships
  commented out in `ci/adapters/` for anyone who wants it.
- Action-only tooling: `lychee-action`, `create-issue-from-file`,
  `create-pull-request`, `sticky-pull-request-comment`, `deploy-pages`,
  `upload-pages-artifact`, `scorecard-action`, `harden-runner`, `actionlint`,
  `zizmor`, `gitleaks-action`, `dependency-review-action`, `actions/labeler`,
  `actions/stale`, `actions/github-script`. Each one has a local CLI that does
  the same job: `lychee`, `gh issue`, `gh pr create`, `gh pr comment --edit-last`,
  a `gh-pages` push, `scorecard`, `gitleaks`, `osv-scanner`, `gh pr edit`, and
  the job scripts themselves.
- TypeScript on Node for the engine. Two runtimes for one repo, and the two
  existing lists are already Python. Node stays as a tooling install.
- `web.archive.org` as the default for dead entries. The guidelines push away
  from archived items in the main list, and a local copy keeps working offline.
  Wayback stays documented as the alternate for `links.archive`.
- Generated list entries. awesome.re requires the list not be AI-generated and
  its own repo does not accept fully AI-generated PRs. Automation here verifies,
  repairs, and publishes. It does not write entries.
- Rewriting a dead main-list URL to a `web.archive.org` snapshot. The guideline
  about unmaintained and archived items points the other way. The entry moves to
  `legacy.md` or comes out.
- Auto-merge on any path that reaches `readme.md`, including a combined
  dependency and content change.
- CI badge in `readme.md`. awesome.re's PR template rejects it, and awesome-lint
  has a `no-ci-badge` rule. The pipeline stays, the badge goes.
- Two link checkers. `dkhamsing/awesome_bot` last committed in April 2023, and
  `tcort/github-action-markdown-link-check` is slower with weaker cache and
  fragment handling. lychee does the job, on a laptop and on any runner.
- `markdownlint-cli2`. awesome-lint already bundles the remark-lint rules this
  repo needs, and a second Markdown linter produces conflicting advice.
- Any LLM call inside a job. Nothing in the pipeline needs a model, and adding
  one puts the "not AI-generated" requirement at risk for no gain.
- Analytics, comment widgets, and external fonts on the site. Cost without a
  reader benefit, plus a privacy surface.
- A server or database. The list is Markdown. Nothing here needs state, beyond
  the `.state/` files that record when a job last ran.
